# OpsWatch — Step 1: Foundations and AWS onboarding

- **Status:** approved design, pending written-spec review
- **Date:** 2026-09-17
- **License:** MIT

## 1. Context

OpsWatch is an open source, self-hosted observability tool for AWS, in the spirit of
Datadog but built incrementally. It grew out of a real production investigation on an
ECS + Aurora stack, where answering simple questions (which client causes the CPU
sawtooth, which Aurora instance is really the writer, which SQL dominates a reader, which
route returns 5xx) required stitching together ECS, ELB, RDS, Performance Insights,
CloudWatch Metrics and CloudWatch Logs Insights by hand. OpsWatch makes that reading
and those analyses available in one interface.

The project is first used by its author, then published for others. It must be easy to
install, safe to connect to a production AWS account, and pleasant to use.

## 2. Roadmap and scope of this spec

The product is delivered in independent steps, each with its own spec, plan and release:

| Step | Content |
|------|---------|
| **1 (this spec)** | App foundations, EN/FR interface, public "Getting started" guide, AWS account connection by three methods, per-service permission test, admin protection |
| 2 | Containers (ECS): clusters, services, tasks, CPU/memory, deployments, events, analyses |
| 3 | Databases (RDS/Aurora): clusters, instances with their real role, CPU, connections, top SQL via Performance Insights, analyses |
| 4 | CloudWatch: metrics, Logs Insights editor, analyses |
| Later | On-demand saving of snapshots from the dashboard, then alerting |

Product direction fixed for all steps: **live reading of AWS plus automatic analyses**,
with no metric storage. On-demand saving comes later and must be addable without
changing the step 1 data model (new tables only).

### Non-goals of step 1

- Any data view beyond the connection test (no ECS/RDS/CloudWatch explorers yet).
- Multi-user, roles, SSO. One admin account only.
- Hosted multi-tenant SaaS operation.
- Metric storage, alerting.

## 3. Deployment model

Self-hosted. Each user runs their own instance with `docker compose up`. The instance
reads the AWS accounts it is connected to; no data leaves the user's infrastructure.

In the role method, "the provider" of the classic cross-account diagram is **the AWS
identity the OpsWatch instance runs with**:

```
Monitored AWS account
│
├── CloudFormation stack (generated by OpsWatch)
│     └── IAM role OpsWatchReadOnly-<id>   (read-only permissions)
│           └── Trust policy: OpsWatch's identity may sts:AssumeRole
│                             only with the matching ExternalId
│
└── OpsWatch instance (docker compose, laptop or AWS)
      └── base identity ── sts:AssumeRole ──▶ temporary credentials (1 h)
```

## 4. Architecture

A single Next.js application (App Router, TypeScript strict). Every AWS call runs on the
server; credentials never reach the browser.

```
opswatch/
├── src/app/[locale]/
│   ├── setup/                     first-run admin creation
│   ├── login/
│   ├── getting-started/           public guide (first page)
│   ├── accounts/                  connected accounts, status per service
│   └── accounts/new/              connection wizard (3 methods)
├── src/app/api/
│   ├── connections/[id]/test      runs the permission test
│   └── connections/[id]/template  returns the generated CloudFormation YAML
├── src/lib/aws/
│   ├── credentials.ts             role | ambient | access keys -> credential provider
│   ├── permissions.ts             one minimal call per service and region
│   ├── template.ts                CloudFormation template generation
│   └── actions.ts                 the IAM action catalogue (single source for template + guide)
├── src/lib/db/                    SQLite via Drizzle, migrations
├── src/lib/crypto.ts              AES-256-GCM, key derived from OPSWATCH_SECRET
├── src/lib/auth/                  admin account, sessions, login rate limit
├── src/components/                UI (shadcn/ui based)
├── messages/en.json, fr.json      next-intl catalogues
├── Dockerfile, docker-compose.yml, docker-compose.test.yml, .env.example
└── README.md, README.fr.md, LICENSE, CONTRIBUTING.md, SECURITY.md
```

## 5. Data model (step 1)

`admin_user`: `id`, `email`, `password_hash`, `created_at`.

`sessions`: `id` (random, stored hashed), `admin_user_id`, `expires_at` (12 h, rolling), `created_at`.

`connections`:

| Column | Notes |
|--------|-------|
| `id` | short random id, also used in the role name suffix |
| `name` | user label |
| `method` | `role` \| `ambient` \| `keys` |
| `aws_account_id` | expected account, verified at test time |
| `regions` | JSON array, at least one |
| `role_arn` | role method only |
| `external_id` | role method only, 32 random bytes base64url, immutable unless regenerated |
| `template_version` | integer, see §6.3 |
| `access_key_ciphertext` | keys method only, AES-256-GCM (iv + tag + ciphertext) |
| `status` | `draft` \| `pending` \| `ok` \| `degraded` \| `failed` |
| `last_test` | JSON: per service and region `{ status, error_code?, checked_at }` |
| `created_at`, `updated_at` | |

Future on-demand saving adds its own tables referencing `connections.id`; nothing here
changes.

## 6. AWS connection

### 6.1 Methods and credential resolution

| Method | Resolution | UI treatment |
|--------|------------|--------------|
| **Role** (recommended) | base identity from the standard provider chain, then `sts:AssumeRole` with `RoleArn`, `ExternalId`, `RoleSessionName = opswatch-<connection id>`, `DurationSeconds = 3600`; credentials cached per connection and refreshed 5 minutes before expiry | "Recommended" |
| **Ambient** | standard provider chain directly (ECS task role, EC2 instance profile, local profile) | shows the detected identity ARN |
| **Access keys** | decrypted in memory at call time, never returned to the browser after save (masked) | permanent warning badge: "for local testing" |

Every `AssumeRole` is logged with the connection id and the result, never with a secret.

### 6.2 Connection lifecycle

1. Wizard step "method" → a `draft` connection is created. For the role method the
   ExternalId is generated and the template becomes downloadable.
2. Role ARN (role method) or keys (keys method) provided → `pending`.
3. Test run → `ok`, `degraded` (reachable, at least one service denied) or `failed`
   (cannot authenticate, wrong account, or every service denied).
4. The test can be re-run at any time from the accounts page.

### 6.3 Generated CloudFormation template

- Resource `AWS::IAM::Role` named `OpsWatchReadOnly-<connection id>`, `MaxSessionDuration: 3600`.
- Trust policy principal: the exact ARN of OpsWatch's base identity when
  `sts:GetCallerIdentity` returns a user or role; the account root otherwise.
  Condition: `StringEquals sts:ExternalId = <external id>`.
- Inline policy: exactly the actions of §6.4, `Resource: "*"` (these describe/list/metric
  actions do not support resource-level scoping in a useful way).
- Outputs: `RoleArn`, `OpsWatchTemplateVersion`.
- The template carries a version. When a later step needs new actions, the version
  increases and the accounts page shows "Update stack" for connections on an older version.
- Delivery: download as YAML; copy-ready AWS CLI command
  (`aws cloudformation deploy --template-file ... --capabilities CAPABILITY_NAMED_IAM`);
  "Launch Stack" button only when `OPSWATCH_TEMPLATE_BUCKET` is set.
- Validated by `cfn-lint` in CI.

The policy OpsWatch's own base identity needs (shown in the guide, step 0):
`sts:AssumeRole` on `arn:aws:iam::*:role/OpsWatchReadOnly-*`, nothing else.

### 6.4 IAM action catalogue

Defined once in `src/lib/aws/actions.ts`; both the template and the guide render from it.
It covers steps 1 to 4 so that users deploy the stack once. It is deliberately narrower
than the AWS managed `ReadOnlyAccess` policy, which allows reading S3 object contents:
OpsWatch never reads S3, Secrets Manager or SSM Parameter Store.

| Service group | Actions | Unlocks |
|---------------|---------|---------|
| ECS | `ecs:ListClusters`, `ecs:DescribeClusters`, `ecs:ListServices`, `ecs:DescribeServices`, `ecs:ListTasks`, `ecs:DescribeTasks`, `ecs:DescribeTaskDefinition`, `ecs:ListContainerInstances`, `ecs:DescribeContainerInstances` | containers view |
| EC2 (read) | `ec2:DescribeInstances`, `ec2:DescribeNetworkInterfaces`, `ec2:DescribeSecurityGroups`, `ec2:DescribeSubnets` | mapping IPs and hosts to services |
| Application Auto Scaling | `application-autoscaling:DescribeScalableTargets`, `application-autoscaling:DescribeScalingPolicies` | min/max tasks, scaling targets |
| ELB | `elasticloadbalancing:DescribeLoadBalancers`, `elasticloadbalancing:DescribeTargetGroups`, `elasticloadbalancing:DescribeListeners`, `elasticloadbalancing:DescribeRules`, `elasticloadbalancing:DescribeTargetHealth` | routing, health checks |
| RDS | `rds:DescribeDBClusters`, `rds:DescribeDBInstances`, `rds:DescribeDBProxies`, `rds:DescribeEvents` | databases view, real writer/reader role |
| Performance Insights | `pi:GetResourceMetrics`, `pi:DescribeDimensionKeys`, `pi:GetDimensionKeyDetails`, `pi:ListAvailableResourceMetrics`, `pi:ListAvailableResourceDimensions` | top SQL, wait events, top hosts |
| CloudWatch Metrics | `cloudwatch:GetMetricData`, `cloudwatch:ListMetrics`, `cloudwatch:DescribeAlarms` | charts |
| CloudWatch Logs | `logs:DescribeLogGroups`, `logs:DescribeLogStreams`, `logs:StartQuery`, `logs:GetQueryResults`, `logs:StopQuery` | Logs Insights; **queries are billed per GB scanned** |

### 6.5 Permission test

1. `sts:GetCallerIdentity` with the resolved credentials; the account must equal
   `aws_account_id`, otherwise `failed` with a clear message.
2. In parallel, per selected region, with a 5 s timeout per call:

| Service | Call |
|---------|------|
| ECS | `ecs:ListClusters` (maxResults 1) |
| ELB | `elasticloadbalancing:DescribeLoadBalancers` (PageSize 1) |
| RDS | `rds:DescribeDBInstances` (MaxRecords 20) |
| Performance Insights | `pi:ListAvailableResourceMetrics` on the first instance with PI enabled; `not_applicable` when none |
| CloudWatch Metrics | `cloudwatch:ListMetrics` (one namespace) |
| CloudWatch Logs | `logs:DescribeLogGroups` (limit 1) |

3. Mapping: success → `ok`; `AccessDenied*`/`UnauthorizedOperation` → `denied` with the
   missing action named; timeout/network → `error`. `logs:StartQuery` is not called
   (billed) and is shown as "checked on first query".
4. The result is stored in `last_test` and rendered as a checklist: green, orange (denied,
   with what the user loses) or red.

## 7. Protecting the instance

- **First run:** when no admin exists, every route redirects to `/[locale]/setup` to create it.
- **Sessions:** random session id in a cookie, `HttpOnly`, `SameSite=Lax`, `Secure` when
  served over HTTPS, 12 h rolling expiry, stored hashed server-side.
- **Login rate limit:** 5 attempts per minute per IP (in memory).
- **Public routes:** `/[locale]/setup` (only while no admin exists), `/[locale]/login`,
  `/[locale]/getting-started`, the `/` locale redirect and static assets. Everything else
  requires a session.
- **API routes:** `Origin` header checked against the instance origin on every mutating
  request.
- **Secrets:** access keys encrypted with AES-256-GCM using a key derived from
  `OPSWATCH_SECRET` (HKDF-SHA256); decryption failure (tampering or changed secret) marks
  the connection `failed` with an explicit message.

## 8. "Getting started" page (first page)

Public, documentation only, fully translated. Sections in order:

1. **Header:** "Connect your AWS account", subtitle "Read-only, revocable at any time,
   nothing leaves your infrastructure".
2. **Method cards:** IAM role (recommended), Running on AWS (ambient), Access keys (quick
   local test). Each links to its own step-by-step block.
3. **How it works:** the §3 diagram as an interactive SVG; hovering or focusing a node
   explains it (stack, role, permissions policy, trust policy, ExternalId, AssumeRole,
   temporary credentials).
4. **Step by step (role method):**
   0. Give OpsWatch an identity: laptop → IAM user limited to the §6.3 base policy (JSON
      shown with a copy button); ECS/EC2 → task or instance role with the same policy.
   1. Create the connection in OpsWatch (ExternalId and template generated).
   2. Deploy the stack: console upload, CLI command, or "Launch Stack".
   3. Paste the `RoleArn` from the stack outputs.
   4. Run the test and read the checklist.
   Shorter equivalents for the ambient and access-key methods.
5. **What each service needs:** one card per service group of §6.4 with the exact actions,
   why they are needed, what they unlock, and what is missing without them.
6. **Security:** what OpsWatch can and cannot do; the ExternalId and the confused deputy
   problem in plain words; how to revoke access (delete the stack).
7. **Troubleshooting:** `AccessDenied` on AssumeRole (ExternalId or trust policy mismatch),
   region not enabled, Performance Insights disabled on an instance, organization SCP
   blocking an action, wrong account id.

## 9. Internationalisation

- Locales `en` (default) and `fr`, prefix in the URL (`/en/...`, `/fr/...`).
- `/` redirects to `/en`, unless the `NEXT_LOCALE` cookie holds a previous choice. The
  browser's `Accept-Language` is not used.
- Language switcher in the top bar; the choice is saved in the cookie.
- No user-facing string in code. A unit test fails if `en.json` and `fr.json` do not have
  exactly the same keys.
- Dates and numbers formatted with the active locale. IAM actions, ARNs, CLI commands and
  code are never translated.

## 10. Interface

- Layout: left sidebar (Getting started, Accounts; Containers, Databases, Logs visible but
  disabled with a "coming soon" label), top bar (account and region selector, language,
  theme).
- Light and dark themes, following the system preference with a manual toggle.
- One accent color, generous spacing, cards for method choice and per-service status.
- Accessibility: full keyboard navigation, visible focus, WCAG AA contrast,
  `prefers-reduced-motion` respected.
- Responsive down to 360 px wide.

## 11. Testing

**Unit (Vitest)**
- `template.ts`: generated YAML contains the role name, the ExternalId condition, the exact
  action catalogue, the version output; trust principal is the identity ARN when known and
  the account root otherwise.
- `credentials.ts`: `AssumeRole` receives `RoleArn`, `ExternalId`, session name and
  duration; cached credentials are reused, then refreshed within 5 minutes of expiry.
- `permissions.ts`: success, `AccessDenied`, timeout and wrong-account cases map to the
  statuses of §6.5; PI `not_applicable` when no instance has it.
- `crypto.ts`: round trip; tampered ciphertext and wrong secret are rejected.
- i18n key parity between `en.json` and `fr.json`.
- Auth: password hashing, session expiry, rate limit.

**End-to-end (Playwright, `docker-compose.test.yml` with moto)**
- First run → admin setup → login.
- Getting started renders in English, language switch to French, choice persists.
- Create a role connection → download template → provide role ARN → run test → checklist.
- Create an access-key connection → keys masked after save → test.
- Unauthenticated access to `/accounts` redirects to login; getting started stays public.

**Static and CI**
- `cfn-lint` on a generated template.
- GitHub Actions: lint, typecheck, unit, end-to-end, Docker image build.

## 13. Definition of done

- `docker compose up` starts the instance; it refuses to start without `OPSWATCH_SECRET`.
- First run creates the admin; afterwards login is required except for public routes.
- The getting started guide is complete in English and French, with the interactive diagram.
- An account can be connected with each of the three methods, and the test shows the
  per-service checklist.
- The generated template passes `cfn-lint`.
- All tests of §11 pass in CI.
- Validation against a real AWS account is a manual step performed by the owner, since it
  requires deploying a stack in that account.
